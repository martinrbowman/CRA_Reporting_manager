# Install / Setup Guide

## Option A: Docker or Podman (recommended)

**Prerequisites:** Docker with the Compose plugin (`docker compose`), or
Podman 4+ (with `podman compose` or standalone `podman-compose`).

```bash
git clone <this repo> cra-compliance-platform
cd cra-compliance-platform
./scripts/start.sh
```

What `start.sh` does, in order:

1. Detects your container engine (`scripts/lib/engine-detect.sh` — prefers
   `docker compose`, falls back through `podman compose` → `podman-compose`
   → `docker-compose`).
2. If `.env` doesn't exist, creates it from `.env.example` with a random
   `JWT_SECRET` and `DB_PASSWORD`.
3. Refuses to start if `ADMIN_EMAIL` is not set in `.env` — edit the file,
   set `ADMIN_EMAIL=you@example.com`, and re-run.
4. If `config/ldap.yml` doesn't exist, copies `config/ldap.example.yml`
   (LDAP starts disabled — see `docs/admin-guide.md` to turn it on).
5. Builds and starts three containers: `db` (Postgres 16), `api` (Fastify,
   runs migrations then the idempotent seed script then the server), `web`
   (nginx serving the built SPA and proxying `/api/` to the api container).
6. Prints the web URL (`http://localhost:${WEB_PORT:-80}`) and, on first
   boot only, the generated admin password.

Stop everything with `./scripts/stop.sh`.

### Using an external Postgres

Set `DATABASE_URL` in `.env` to point at it and remove/ignore the `db`
service in `docker-compose.yml` if you don't want a local Postgres container
at all.

### Podman notes

- Rootless Podman with named volumes (`db_data`) needs no special handling.
- If you bind-mount host paths instead (not the default setup) on an
  SELinux-enforcing host, add a `:Z` suffix to the mount in
  `docker-compose.yml` — check with `command -v getenforce`.
- Standalone `podman-compose` has historically been inconsistent about
  honoring `depends_on: condition: service_healthy`. `start.sh` polls for a
  "healthy" status itself after `up -d` regardless of which compose
  implementation is in use, so this is handled either way — if a dependent
  container starts before its dependency is ready, its restart policy
  (`unless-stopped`) will retry it until the dependency comes up.

## Option B: Bare-metal / PM2 (embedded/ARM targets)

For deployments where running three containers is unwanted overhead — e.g. a
Raspberry Pi or similar embedded target — use the PM2 path instead.

**Prerequisites:** Node >=22.5, pnpm >=9, [PM2](https://pm2.keymetrics.io/)
(`npm install -g pm2`), a system nginx, and a reachable Postgres (local or
remote).

```bash
cp .env.example .env      # fill in DATABASE_URL, JWT_SECRET, ADMIN_EMAIL
cp config/ldap.example.yml config/ldap.yml   # optional, LDAP starts disabled
./scripts/start-baremetal.sh
```

This installs dependencies, builds all three packages, runs migrations and
the seed script, starts the API under PM2 (`ecosystem.config.js`), and
generates an nginx config from `nginx/cra-platform.conf` with the repo path
substituted in. The script prints the exact `cp`/`ln -s`/`reload` commands to
install it — it does not touch system nginx config itself (usually needs
`sudo`).

Stop the API with `./scripts/stop-baremetal.sh` (`pm2 stop cra-api`).

## Environment variables

See `.env.example` for the full list with inline comments. The ones you must
set yourself: `DB_PASSWORD` (auto-generated by `start.sh` in the Docker path;
set manually in `.env` for bare-metal), `JWT_SECRET` (same), `ADMIN_EMAIL`
(always required). Everything else has a working default or is optional
(SMTP, CORS_ORIGIN if not serving from `http://localhost`).

LDAP/AD is configured via `config/ldap.yml`, not environment variables — see
`docs/admin-guide.md`.
